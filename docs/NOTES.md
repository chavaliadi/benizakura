# Benizakura — Engineering Notes & Research Roadmap

## Current Goal
Build the initial skeleton for **Benizakura**, establishing a clean, maintainable, and typed foundation for an AI regression-testing and evaluation-gating system ("CI for AI behavior").

## Current Target
- **Application**: **Conquer** (AI-powered technical interview prep platform)
- **Feature**: **Per-Question Answer Scorer & Profile Generator** (`POST /api/interview/score`)
- **Nature of Feature**: Evaluates candidate interview answers against technical rubrics, generates numeric scores (0.0–10.0), provides diagnostic feedback, and emits skill profile deltas.

## Current Scope
Prompt and application AI behavior regression testing:
- Freezing an evaluation set of candidate answers and questions.
- Replaying baseline vs candidate prompts/configurations.
- Measuring scoring distribution shifts, score regressions, and qualitative critique drift.
- Gating CI/CD with automated `PASS`, `FAIL`, or `INCONCLUSIVE` verdicts.

## Current Status
- **Core Pairwise, Rubric, Statistical & LLM Judge Layer Implemented**:
  - Typed domain models (`EvaluationCase`, `EvaluationResult`, `EvaluationRun`, `Verdict`, `ComparisonResult`).
  - Rubric contract and criteria validation with non-empty strings, non-negative weights, evaluation instructions, and domain-independent standard criteria library (`StandardCriteria`).
  - Structured judge judgments (`PairwiseJudgment`) supporting per-criterion assessments (`CriterionAssessment`), evidence quotes, confidence bounds, and serialization round-trips.
  - Pairwise protocol (`PairwiseJudge`) and deterministic test doubles (`MockPairwiseJudge`, `MockJudgeProvider`).
  - `BidirectionalPairwiseRunner` executing presentation-swapped passes, normalising both overall and criterion-level winners, and classifying position instability.
  - Evaluation dataset abstraction (`EvaluationDataset`, `EvaluationSample`) preserving case identity mappings and enforcing uniqueness.
  - Deterministic statistical analysis engine (`StatisticalAnalyzer`, `StatisticalAnalysis`):
    - Empirical candidate/baseline/tie win rates and consistency rates with explicit sample-size denominators.
    - Criterion-level aggregation (`CriterionAggregate`) without fabricating missing criteria.
    - Paired difference per-case modeling ($D_i \in \{-1.0, 0.0, +1.0\}$) and explicit regression tracking (`get_regressed_cases()`, `get_improved_cases()`).
    - Paired bootstrap resampling with replacement estimating percentile confidence intervals around win-rate differences.
    - Effect size representation (`EffectSize`) with net win rate delta and Cohen's $g$ for decisive pairs.
  - Provider-independent LLM Judge abstraction:
    - Generic `JudgeProvider` protocol (`generate(JudgeRequest) -> JudgeResponse`) with zero vendor SDK leakage.
    - `JudgePromptBuilder` generating position-symmetric, instruction-guided prompts without leaking candidate/baseline identities.
    - `JudgeResponseParser` validating JSON structure, markdown code fences, schema semantics, and rubric criterion containment.
    - Explicit, typed error hierarchy (`JudgeParseError`, `JudgeValidationError`, `JudgeProviderError`).
    - `LLMPairwiseJudge` orchestrating prompt construction, provider completion, and response validation.
  - Provisional `SimpleComparator` implementing clear regression detection and improvement gating for pointwise runs.
  - 5 placeholder development cases in `evals/conquer/cases.json`.
  - Interactive CLI entry point (`benizakura` / `python3 -m benizakura.cli`).
  - Unit test suite running via `pytest` (**113 passing tests**).
- **Evaluation Methodology**: Statistical paired bootstrap evaluation core and provider-independent LLM judge abstraction implemented. Live LLM vendor adapters (Groq, Anthropic, OpenAI) and release gating policies planned for subsequent phases.

## Research To Review

Before finalizing the evaluation engine, we will conduct a deep literature review across the following core areas:

1. **LLM-as-a-Judge Foundations**:
   - Zheng et al. (2023), *"Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena"*
   - Single-answer grading vs pairwise comparison trade-offs.
   - Reference-guided grading vs reference-free grading.

2. **G-Eval & Rubric-based Evaluation**:
   - Liu et al. (2023), *"G-Eval: NLG Evaluation using GPT-4 with Better Human Alignment"*
   - Multi-criteria breakdown, step-by-step evaluation generation, and probability-weighted scoring.

3. **Judge Bias Identification & Mitigation**:
   - **Position Bias**: Sensitivity to presentation order in pairwise setups.
   - **Verbosity Bias**: Tendency to assign higher scores to longer, structured responses even when content is shallow.
   - **Self-enhancement / Model Familiarity Bias**: Tendency of models to favor outputs generated by their own family.
   - **Bandwagon / Anchor Bias**: Leniency drift when previous turns or greetings precede the answer.

4. **Calibration & Consistency**:
   - Techniques for aligning LLM judge scores with senior human engineers.
   - Temperature settings (`temperature=0` vs multi-sample consensus).
   - Measuring inter-rater reliability (Krippendorff's alpha, Cohen's kappa).

5. **Regression Testing & Statistical Gating**:
   - Paired difference testing and bootstrap confidence intervals.
   - Defining meaningful effect sizes (how much score drop constitutes a true regression vs sampling noise).
   - Defining the boundary conditions for `INCONCLUSIVE` when variance is high.

6. **Benchmark Design**:
   - Constructing a rigorous 25–30 case benchmark specifically for Conquer's answer scorer.
   - Stratified sampling across tracks: Data Structures, System Design, Behavioral (STAR), Frontend/Backend.
   - Golden reference answers, subtle technical bugs, and known edge cases.
